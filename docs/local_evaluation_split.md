# ローカル評価セットの分割方法

公開パック187タスクから、開発151タスク・未知タスク検証36タスクを選んだ案。
具体的なID・seed範囲は [split.yaml](../evaluation/local_v1/split.yaml)、指示文を含む全タスクの割当表は
[tasks.csv](../evaluation/local_v1/tasks.csv) に保存した。タスクの成功率や難易度の実測を使って選んだものではない。
シミュレータは実行していない。BEHAVIORの別インスタンスは実在・読み込みとも未確認。

## 評価を2つに分ける

| 環境 | 開発タスク | 既知タスク検証 | 未知タスク検証 |
| --- | ---: | --- | ---: |
| Robosuite | 7 | 同じ7タスク、別seed | 0 |
| LIBERO | 104 | 同じ104タスク、別layout | 26 |
| BEHAVIOR | 40 | 同じ40タスク、別の公開instanceがあるものだけ | 10 |

「既知タスク検証」と「未知タスク検証」は別々に集計する。
前者は既知の操作・指示の別配置への頑健性、後者は開発に使わなかったタスク群への転移を見る。
未知側に置いたタスクは、初期状態だけを変えて開発に使うこともしない。
動作確認の既存履歴は、ユーザーの指示により今回の分割選定では考慮していない。
分割を採用した時点から隔離を開始し、隔離対象のデータを含む暫定adapterを使う場合には、その評価を
「追加学習でも未見」とは表現しない。ただし、Robosuiteの7タスクはタスク数が少ないので、未知タスク検証は行わない。未知タスク検証のスコアはLIBEROとBEHAVIORのタスクで行う。

## タスクの選び方

タスクIDの一様ランダム分割ではなく、同じ目的や近い派生タスクをまとめる。
ただし全操作プリミティブを完全に分離する設計ではない。既知の操作を未知の物体・対象・組み合わせへ
転移できるかも評価したいので、例えば「個別の食品をバスケットへ入れる」を開発し、
「指定された食品2つを入れる」を未知側に置くことは認める。

### LIBERO

次のまとまりを未知側に置く。合計26タスク。

| まとまり | ID（`90_`等は`libero_90_`等の略） | 数 |
| --- | --- | ---: |
| 食品2つをバスケットに入れる | `10_0, 10_1, 10_7` | 3 |
| 本をキャディの各区画へ入れる | `10_5, 90_73, 90_74, 90_75, 90_77, 90_78, 90_79, 90_80, 90_81, 90_82, 90_83` | 11 |
| バターを引き出しへ入れて閉める | `90_3, 90_4` | 2 |
| ボウルの積み重ねと、その後のトレイへの配置 | `90_16, 90_17, 90_63, 90_64` | 4 |
| ワインボトルをラックへ置く | `90_27, goal_9` | 2 |
| ケチャップをバスケットへ入れる | `90_48, object_4` | 2 |
| オレンジジュースをバスケットへ入れる | `90_53, object_9` | 2 |

残り104タスクを開発側に置く。別suiteの同じ目的もまたいでまとめた。
例：`libero_90_48` と `libero_object_4` はともにケチャップをバスケットに入れるため、
片方だけを未知として数えない。

手元のLIBERO-PROにあるBDDLのゴール述語を照合し、物体の出現番号を除いて同じゴールになる
83グループが開発側と未知側にまたがらないことを確認した。
これは重複候補の点検であり、全ての意味的な類似・包含関係を検出した保証ではない。
本をキャディへ入れるタスクが11件を占めるため、ID単位の平均だけでなくまとまり単位の平均も残す。

### BEHAVIOR

次の5組、計10タスクを未知側に置く。残り40タスクは開発側。

- 玩具の片付け：`collecting_childrens_toys`、`picking_up_toys`。
- 食材を切る：`chop_an_onion`、`slicing_vegetables`。
- 噴霧：`spraying_for_bugs`、`spraying_fruit_trees`。
- 缶詰：`can_meat`、`canning_food`。
- 箱・本の収納：`boxing_books_up_for_storage`、`moving_boxes_to_storage`。

これはタスク名・公開指示による暫定的な分類。実行前に公開の目標条件・シーン構成を確認し、
開発側にほぼ同じタスクがあればまとまりを見直す。失敗率を見て簡単なタスクへ差し替えない。

## 初期状態の分割

### Robosuite

- 開発seed：301〜400。
- 検証seed：401〜420。

既知・未知の両検証で同じ検証用seed範囲を使ってよい。異なるタスク間で同じseed値を使うことは
データの重複ではない。一方、seedが違うことだけで見た目や課題が十分に違うと保証されるわけではない。

### LIBERO

手元にある公開130タスクの初期状態ファイルを静的に点検し、全て先頭次元が50であることを確認した。
モデルやシミュレータは起動していない。配置IDは `(seed - 1) % 50` で決まる。

| 用途 | layout ID | 使用seed |
| --- | --- | --- |
| 開発 | 0〜19 | 301〜320 |
| 検証 | 40〜44 | 441〜445 |

既知・未知の両検証で同じ検証用seed範囲を使ってよい。

### BEHAVIOR

`seed` は乱数ではなく、事前にサンプルされたタスクインスタンスの番号。

- 開発：instance 0~19を開発用とする。
- 検証：instance 100~104を使用する。

## 実行と集計

最終的な比較は提出時と同じgateway・観測制限を通す。採点用の成功・正解状態をエージェントへ渡さない。
baselineのローカル評価は設定・経路が異なるため、最終スコアと同一視しない。
`split.yaml`は評価プロトコルであり、gatewayに直接渡せる`pack.yaml`ではない。

既知タスクの検証を全て回すと、既知側はRobosuite 140試行＋LIBERO 520試行＋BEHAVIOR 200試行。
未知側はRobosuite 0試行＋LIBERO 130試行＋BEHAVIOR 50試行を計画する。

環境別・既知/未知別の6区分を報告し、それぞれ試行成功率、タスク平均、グループ平均、実行時間を残す。
本番の重みは非公開なので、手元の合成値を本番スコアとは呼ばない。
設定変更前後は同じタスク・状態・上限・時間予算で比較する。
